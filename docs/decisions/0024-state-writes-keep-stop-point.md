# 0024 · 只写状态值时保持流程停点

- 状态：已实现
- 日期：2026-11-12
- 关联：[0021](0021-run-process-lifecycle.md)（Run 进程生命周期）。

## 背景

1. 服务端在流程停下时多处写入状态值：决策点批复、澄清与升级答复、暂停与继续、中断标记、超时记录、修改节点 Skill 与角色模型、成本记录。这些写入原先都不指定来源节点，由 LangGraph 推断。
2. LangGraph 把这类写入记在“最后执行过的节点”名下，并重新计算该节点的出边。服务端用 `update_state(None, as_node=X)` 改写过走向时（升级后选择继续、澄清答复后回到测试性评估），节点 X 并不会被记为“执行过”，推断出的仍是更早的节点，例如出边指向结束的 `workflow_escalate`。
3. 结果是：升级选择继续后停在决策点，再提交驳回，下一节点变为空，驳回被吞掉，本轮被判为已完成。超时巡检和修改节点 Skill 在同一时刻写入，也会造成同样的问题。

## 决定

1. **统一入口。** 只写状态值的调用一律经 `GraphRunService._write_values`，不再直接调用 `update_state(cfg, values)`。需要改写走向的调用仍显式指定 `as_node`，不经此入口。
2. **先按默认推断写入，再核对停点。** 写入前记下当前停点；写入后停点不变即结束，这是绝大多数情况。
3. **停点丢失时重写。** 从写入前的检查点重写，依次把写入记在停点的前驱名下：固定边指向停点的节点，以及条件边去向中含停点或未声明去向的节点。停点复原即结束。
4. **无法复原时恢复并报错。** 复制写入前的检查点作为最新状态，抛出 `HitlError`，不让流程静默结束。
5. **流程执行中不修复。** 本进程正在执行图，或最新检查点已不是本次写入产生的那一个时，停点变化可能来自流程自身的推进，不做重写。

## 后果

- 停点丢失时，检查点历史中会多出写入前检查点的分支，记录的是被放弃的写入。
- 自定义流程与内置流程共用这一入口，回归测试见 `tests/test_selected_workflow.py` 中的升级后驳回用例。
