# 0028 · 回退升级后选择继续即重做一次

## 背景

1. 回退次数用完后，本轮停下等人处理，待办类型为升级，人可选择继续、暂停或终止。决策记录把「继续」写作「继续重试」。
2. 服务端处理「继续」时调用 `update_state(None, as_node=X)`。LangGraph 对 `as_node` 的含义是「节点 X 刚执行完」，下一步取 X 的出边，而不是重新执行 X。
3. 内置通用软件开发流程由系统节点「回退升级」接住评审、测试、质量门禁的超限失败，不记录升级来源，服务端按「开发」处理，结果下一步成了开发之后的「变更」，开发被跳过。
4. 自定义流程记录了升级来源（未通过的那个节点），继续后从该节点之后往下走，等于放行一次未通过的结果，与「继续重试」的字面含义不符。

## 决定

1. **继续即重做一次。** 自定义流程回到升级来源节点的回退目标重新执行；内置通用软件开发流程回到「开发」重新执行。回退次数不清零，重做后仍未通过时再次停下等人处理。
2. **用 `Command(goto=...)` 指定下一步。** 写入记在升级节点名下，下一步直接是重做的起点，不再借用 `as_node` 推断。
3. **重做的起点看得到失败原因。** 回退次数用完时也写入 `return_feedback`（「「节点名」未通过：……」），与未超限时的回退一致。
4. **并行汇合冲突不变。** 处理冲突后继续，仍从汇合节点之后执行（见 ADR 0016）。并行支路内不允许回退，没有支路内重做的情形。

## 后果

- 「继续」不再放行未通过的结果。确需跳过时，应改流程或终止本轮。
- 每次选择继续只多跑一轮，模型调用次数随之增加。
- 回归测试：`tests/test_structured_verdict.py::test_escalation_continue_reruns_developer`、`tests/test_selected_workflow.py::test_gate_rejection_after_escalation_continue_takes_effect`。
