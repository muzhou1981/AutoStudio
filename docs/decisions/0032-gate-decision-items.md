# 0032 · 决策点的逐项审批

- 状态：已接受；第一步已实现，第二、三步待进行
- 关联：扩展 [0031](0031-parallel-branches-and-compare.md) 之前的「批准或驳回」决策点；不改变「择一」决策点。

## 1. 背景

1. 决策点只有一个整体结论：批准或不通过。一次评审往往要核对几项内容（例如接口兼容、安全、测试覆盖），人只能在附言里逐条写，下游活动要从自由文本里辨认哪几条不通过。
2. 待办已能列出多份待审阅产物，但只供阅读，不能分别给结论。
3. 需求澄清的「A/B/C」选项是从正文里猜出来的，不在流程定义里，不适合承担审批语义。

## 2. 方案

### 2.1 定义

「批准或驳回」决策点可以带若干**决策项**，不写时与现在完全一致：

```yaml
- id: arch_review
  kind: gate
  decision: approve
  reject_to: architect
  items:
    - id: api
      title: 接口向后兼容
      hint: 对照接口说明逐条核对
      required: true        # 缺省为 true
  pass_rule: all            # all（缺省）| manual
```

- `items`：标识在决策点内唯一，名称必填；最多 30 项。
- `pass_rule`：
  - `all`：全部必答项通过才放行，任一项不通过即按「不通过」去向退回；整体结论由逐项结论得出，人不再单独选。
  - `manual`：条目只作核对清单，整体结论仍由人选。
- 「择一」决策点不能带决策项。

### 2.2 批复

- 网页批复提交 `item_decisions`：每项 `{id, decision: approved|rejected, note}`。不通过的项必须写原因；`all` 规则下必答项都要作答。
- 未提交 `item_decisions` 而整体「批准」时（例如飞书卡片的「全部通过」），视为全部通过；`all` 规则下整体「不通过」必须逐项给出，以便下游知道退回的原因。
- 逐项结论按「通过「X」」「不通过「Y」：原因」逐行追加到附言，下游活动照常从附言读取；同时写入 `decisions.jsonl` 的 `items` 字段，运行页的决定记录按项展开。
- 整体结论仍写 `gate_decision`，路由不变。
- 实现时发现，任何决策点不通过时人的附言都没有交给要前往的活动。现在不通过时把附言（含逐项结论）写入 `return_feedback`，要前往的活动在「需要修复的问题」里读到，该活动通过后清空；这一点对没有决策项的决策点同样生效。

### 2.3 界面

- 流程编辑页：决策点右栏增加「决策项」：逐项编辑名称、说明、是否必答，可增删与上下移动；下方选择汇合规则。画布上决策点名称后显示「· N 项」。
- 运行页：待办里每项一张卡片，有「通过 / 不通过」分段按钮和备注；顶部汇总「已决 m/n · k 项不通过」与「其余全部通过」；提交按钮文字随汇总变化，必答项未答完时不可提交并说明还差几项。
- 飞书卡片：只放摘要（共几项、几项必答）与「全部通过」「在网页逐项处理」两个按钮，不在卡片上逐项操作。

## 3. 分步

1. 第一步（已实现）：固定条目、`all` 与 `manual` 两种规则、运行页逐项作答、决定记录、编辑页条目编辑与校验、飞书卡片摘要。
2. 第二步：条目由上游产物列出（`items_from`），约定产物中的条目代码块格式；需同步修改相关角色说明（`roles/` 由人工维护）。
3. 第三步：退回后再次进入时沿用上一轮已通过的条目、逐项作答草稿存服务端、泳道格子显示作答进度。

## 4. 取舍

- 不新增状态通道：逐项结论只在批复时汇总成整体结论与附言，状态定义（人工维护的 `default.py`）不变。
- 飞书卡片不做逐项按钮：卡片交互一次只能回传一个值，逐项操作要多次往返，体验与可靠性都不如网页。
