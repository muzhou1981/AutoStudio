# 0010 · 判定类活动使用结构化结论

- 状态：已实现
- 日期：2026-11-11
- 关联：[问题与改进方案](../plans/architecture-remediation.md) C1、C2、C3、D2；取代 [0009](0009-runtime-correctness.md) 中「失败时在正文追加 `STATUS: fail`」的约定。

## 背景

评审、测试、QA 的结论原先来自文本约定：默认图的代码评审直接沿用状态里的预设值，从不读取评审输出；编译器用正则 `^STATUS: fail$` 判定回退；验收对照只要求证据文本中「出现」验收编号。模型写出编号即视为覆盖，漏写失败标记即视为通过，失败是开放的。

返工时程序员也看不到失败原因；程序员的变更请求没有机器可读的格式，变更控制分支实际不可达。

## 决定

1. **结论块。** 判定类活动（默认图的评审、测试、QA；编译器中配置了 `returns_to` 的活动和测试工程师的 `test_report` 活动）在正文末尾输出 `verdict` 围栏块，内容为 JSON：`status`（`pass`/`fail`）、`ac`（验收编号到 `pass`/`fail`/`untested`）、`summary`。解析在 `verification/verdict.py`。
2. **失败即关闭。** 真实后端缺少结论块或结论块格式错误，按未通过处理，并把原因写进报告。Stub 后端没有真实判断能力，沿用状态中的预设结论，只用于调试分支。旧的 `STATUS: fail` 行仍识别为失败，作为兼容。
3. **验收对照。** 一个验收编号通过须满足其一：QA 结论块中该编号为 `pass`；或验证命令退出码为 0 且其输出含该编号。正文提及不再算覆盖。仅模拟运行退回到「出现即覆盖」，对照表中注明「模拟运行（无真实证据）」。
4. **测试结论。** 执行了验证命令时以退出码为准；测试工程师给出了结构化结论时，结论与命令须同时通过。
5. **返工反馈。** 判定未通过时写入 `return_feedback`（失败活动名与完整报告）；被退回的活动在提示词中以「需要修复的问题」呈现，执行后清空。
6. **变更请求。** 程序员以 `change_request` 围栏块提出变更（`impact`：`scope`/`architecture`）。默认图的变更控制据此回到需求或架构关卡，并在路由后消费该请求，避免关卡批准后再次回到关卡。
7. **多产物切分。** 一次调用产出多个产物时，按同名围栏块或同名标题切分；`change_request` 找不到时为空，不再复制整段正文。

## 后果

- 真实模型漏写结论块会导致一次返工，而不是被静默放行；回退上限与升级机制兜底。
- 角色说明中不需要再写「最后一行写 STATUS: fail」之类的约定，结论格式由引擎在提示词中统一给出。
- 结论块只覆盖通过与否和验收编号，不承载完整的缺陷列表；缺陷仍以正文呈现，并通过 `return_feedback` 原样交给返工方。
