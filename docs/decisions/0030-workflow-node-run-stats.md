# 0030 · 流程节点的运行数据叠加

## 背景

1. 改流程时想知道哪些节点常被退回、常升级、耗时长或耗费多，但运行数据只能逐轮在运行页查看。
2. 现有记录里，回退次数在检查点 `return_counts`（按扁平节点标识），升级与决策点结论在 `decisions.jsonl`，会话按节点归档在 `conversations/nodes/<节点>/<序号>.jsonl`；会话记录不带时间，模型用量只写进按角色记账的 `cost_ledger`，无法归到节点。

## 决定

1. **会话记录补时间与用量。** `begin_turn` 写入 `at`；`finish_turn` 写入 `at` 与可选的 `usage`（`input_tokens`、`output_tokens`）。Cursor 与 Codex 后端在结束一次调用时传入用量。旧运行没有这些字段，只计次数。
2. **服务端汇总。** `GET /api/workflows/{id}/stats` 读取每个运行的最新检查点，只取 `workflow_id` 等于该流程的运行，按节点给出：经过它的运行数、执行次数（会话数）、平均耗时（有时间的会话）、回退次数、升级次数、决策点驳回次数与 token 合计，另给参与汇总的运行数。
3. **按顶层节点归并。** 子图与并行展开后的标识形如 `<顶层标识>__…`，归到对应的顶层节点；当前流程里已不存在的节点不展示。
4. **编辑页按需显示。** 「更多」里有「显示运行数据」开关，打开后各节点下方叠加一行简要数字（前两项），悬停看全部；右栏流程说明下写明汇总了几次运行。开关记在浏览器本地，关闭时不请求数据。
5. **只读，不改变运行。** 汇总不写任何文件，也不影响运行快照。

## 后果

- 内置「通用软件开发」由默认图执行，检查点里没有 `workflow_id`，暂不汇总；自建流程与按自建方式编译的内置流程可以汇总。
- 平均耗时是一次调用从发出到收到结果的时长，不含等待人工的时间。
- 运行很多时，每次打开都要扫描全部检查点与会话文件；数量变大后再考虑缓存或索引。
- 回归测试：`tests/test_workflow_defs.py::test_node_stats_merge_runs_by_top_level_node`。
