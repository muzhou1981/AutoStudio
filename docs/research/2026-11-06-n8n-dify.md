# n8n 与 Dify 对照分析

- 日期：2026-11-06
- 对照对象：AutoStudio。固定 LangGraph 流程、角色产物契约、人工关卡、项目配置与共性配置分离、运行状态可查询
- 性质：检索结论，不是已接受的技术决策
- 前文：[同类 Agent 任务编排的 Web 界面调研](2026-11-06-agent-orchestration-web-ui.md)

## 1. 目的

n8n 与 Dify 都把「多步自动化」做成可视化产品，但解决的问题不同。n8n 把外部系统串成一条可暂停、可重试的执行。Dify 把模型调用放进一条可发布的应用流程，并在需要判断时把人接进来。

AutoStudio 已经选定 LangGraph 作为工厂流程，角色和产物模板写在仓库里，不在网页上自由拼图。本文只摘适合工厂控制台吸收的做法：执行记录、人工暂停、配置边界、节点之间的数据契约、失败后的去向。

检索日为 2026-11-06。材料来自两家官方文档与产品说明，未登录其云端生产环境逐项点击。

## 2. 两款产品各自在做什么

| | n8n | Dify |
|---|---|---|
| 产品形态 | 工作流自动化。节点连接 API、数据库、定时器和表单 | 大模型应用平台。Workflow、Chatflow 与 Agent 共用节点库 |
| 图的地位 | 图就是产品。业务人员在画布上改流程 | 图是应用的运行骨架。模型只是其中一类节点 |
| 人的位置 | Wait 节点暂停执行，用表单或 Webhook 恢复；工具调用前也可以要求人工批准 | Human Input 节点暂停流程，表单上的按钮决定后续分支，并有超时分支 |
| 配置 | 凭证与工作流分开存放，保存时做连通测试，可按项目隔离 | 模型供应商、知识库、工具授权放在工作区；节点用变量引用上游输出 |
| 一次运行 | 执行记录与流程版本分开。状态包括失败、运行中、成功、等待 | 同一次运行可查看节点输出、变量、路径和日志，并可把追踪推到外部观测平台 |

## 3. n8n 值得借鉴的地方

### 3.1 执行记录与流程定义分开

n8n 把「这次跑过」和「流程现在长什么样」分成两套历史。Executions 是运行记录，Workflow history 是流程版本。单条工作流和整个实例都有执行列表，可按失败、运行中、成功、等待，以及开始时间筛选。

失败后的重试保留已经成功的节点结果，只重跑尚未完成的部分。已完成节点不会因为重试再执行一遍。若失败点是子流程，则整段子流程从头再跑。重试本身记成一次新的执行。成功但结果不符合预期的运行不能直接重试，只能把当时的数据拷回编辑器再跑。

对工厂的含义：一轮 Run 是执行记录，场景和项目配置是流程定义，二者不要混在同一份历史里。节点失败或人工驳回之后，已完成节点的产物应保留，只从失败或被退回的节点继续。现在的轨道已经能标出完成、进行中和未到，还缺一份可筛选的运行列表，以及「从这一格重试、前面的格子不重做」的明确语义。

来源：[单条工作流的执行记录](https://docs.n8n.io/build/understand-workflows/understand-executions/view-executions-for-a-single-workflow)、[全部执行记录](https://docs.n8n.io/build/understand-workflows/understand-executions/view-all-executions)。

### 3.2 暂停是流程的一等状态

Wait 节点把执行数据卸到数据库，恢复条件满足后再装回并继续。恢复条件可以是一段时间、指定时刻、一次 HTTP 调用，或一次表单提交。每次执行有自己的恢复地址 `$execution.resumeUrl`，同一条流程里可以有多个 Wait，按调用顺序逐个恢复。短于 65 秒的等待不落库，进程内继续；更长的等待才落库。执行列表用 Waiting 表示这种暂停。

AI Agent 的工具还可以在真正调用前要求人工批准，渠道包括对话、Slack、Telegram 等。这是工具级的闸门，不是整段流程的关卡。

对工厂的含义：需求确认、架构评审、最终交付应像 Waiting 一样成为可查询的阶段，而不是一轮「卡住了」。飞书卡片上的批准、驳回、澄清，应对应这条运行专属的恢复动作。工具级批准可以后做，先把三个关卡做稳。

来源：[Wait 节点](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.wait)、[等待](https://docs.n8n.io/build/flow-logic/wait)、[Tools Agent 的人工复核](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent/tools-agent)。

### 3.3 凭证与流程分开，并按项目隔离

凭证是独立对象，不写进节点参数的明文里。保存时 n8n 会做连通测试。实例若支持项目，凭证可以放在个人空间或某个项目里。OAuth 凭证还可选固定凭证或终端用户凭证：固定凭证无论谁触发都用同一套；终端用户凭证只属于触发这次运行的人。节点上也可以用表达式在运行时选择凭证。

对工厂的含义：这和已经拆开的两层配置一致。Agent 后端、模型、API Key、默认工作区、飞书凭据属于工厂级「配置」，保存后应能看出是否可用，页面不回显密钥。某个待开发项目的场景、工作区目录、通知对象属于「项目配置」，一轮运行只引用项目，不在运行页再选一遍场景。

来源：[创建和编辑凭证](https://docs.n8n.io/build/understand-workflows/create-and-edit-credentials)。

### 3.4 Agent 是根节点，模型、记忆和工具是挂上去的子节点

n8n 用 LangChain 的集群节点：AI Agent 是根，聊天模型、记忆、工具、输出解析器是子节点。记忆只挂在 Agent 上，不挂在普通 Chain 上。Simple Memory 只保留当前会话里最近若干轮，队列模式下不能保证每次都打到同一个 worker，因此不适合当生产记忆。工具调用走函数调用接口，并可附带结构化输出解析。

对工厂的含义：角色仍由 `roles/<name>/role.md` 定义，不在网页上把模型、记忆、工具拖成一张新图。可以借鉴的是输出形状：最终产物、工具调用记录、推理痕迹、迭代次数、是否成功，分开存放。重试上限应对齐 Dify 的 Max Iterations 和工厂已有的开发重试上限，而不是让角色无限调用工具。

来源：[AI Agent](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent)、[LangChain 概念如何落到节点](https://docs.n8n.io/build/integrate-ai/langchain-in-n8n)、[记忆](https://docs.n8n.io/build/integrate-ai/understand-ai-components/how-memory-works)。

## 4. Dify 值得借鉴的地方

### 4.1 流程是约束，模型只是其中一个节点

Dify 把 Workflow 写成应用的运行骨架：输入、检索、模型、工具、分支、代码、人工审核和输出按顺序接好。Workflow 适合一次跑完的批处理；Chatflow 是每条消息走完同一条流程再回复。模型节点之外，还有问题分类、条件分支、迭代和代码节点。失败可以停住、返回默认值，或带着类型化的错误走进恢复分支。

对工厂的含义：角色执行应包在固定顺序里，前后有检查和退路。测试失败退回开发、变更退回需求或架构，应是图上的分支，并带重试上限，而不是让一个 Agent 自己决定要不要跳过 QA。单节点失败时，保留已完成产物，并走到升级给人的分支，而不是整轮无记录地消失。

来源：[Dify Workflow Studio](https://dify.ai/zh/workflows)。

### 4.2 人工介入是节点，按钮就是分支

Human Input 在流程运行到该节点时暂停，把一张表单交给指定的人。表单可以用 Markdown 和上游变量展示待审内容，用段落、下拉、文件收集回复。每个按钮有显示名和动作标识，点下去走不同的边。例如通过、采用人工修改、要求模型按反馈重写。默认等待 3 天，超时走单独的边；这条边没接上，流程就结束。邮件方式把链接发给工作区成员或外部邮箱，第一个响应会关掉这次请求。

对工厂的含义：关卡卡片上的「批准」「驳回」「继续」「暂停」「终止」应对应图上的边，而不是一段自由文本再由模型猜意图。澄清答复和驳回原因适合做成表单字段，预填上游产物，让人在产物上改，而不是从空白处重写。超时未批复应有明确去向，例如通知项目经理或停在原地并保持「等待人工」，不要静默结束。

来源：[人工介入](https://docs.dify.ai/zh/self-host/use-dify/nodes/human-input)、[Human Input 节点说明](https://dify.ai/blog/the-human-input-node-bringing-human-judgment-into-automated-workflows)。

### 4.3 节点之间用变量传递，知识检索与角色分开

Dify 的节点输出是下游可引用的变量。提示词里用 `/` 或 Jinja2 插入上游结果，而不是把整段对话再贴一次。知识检索是独立节点：指定查询、知识库、重排和分数阈值，输出分段数组。知识库本身还有召回测试，用来在接入应用之前检查检索是否对准。

Agent 节点单独配置策略（函数调用或 ReAct）、可用工具、工具说明、最大迭代次数和记忆窗口。输出包括最终回答、每次工具结果、推理痕迹、迭代次数、是否成功，以及结构化日志。

对工厂的含义：角色之间已经约定用产物协作。界面上应能看到这一格消费了哪些上游产物、写出了哪一份。场景知识、模板和领域资料不要只写进角色提示词；至少要能单独检查「这个场景会把什么材料交给角色」。Agent 的迭代次数和工具日志适合挂在节点检视里，供复盘打分，而不必把模型原文铺开。

来源：[Agent 节点](https://docs.dify.ai/en/cloud/use-dify/nodes/agent)、[知识检索](https://docs.dify.ai/zh/self-host/use-dify/nodes/knowledge-retrieval)、[知识库](https://docs.dify.ai/zh/cloud/use-dify/knowledge/overview)、[Agent 节点教程](https://docs.dify.ai/en/learn/tutorials/workflow-101/lesson-08)。

### 4.4 同一条流程贯穿测试、发布和追踪

Dify 强调原型和投产用同一条 Workflow。可以只跑一个节点，或跑整条流程。发布历史可回滚，DSL 可在工作区之间迁移。运行追踪可推到 Langfuse、LangSmith、Arize、W&B Weave。

对工厂的含义：场景和项目配置应有可追溯的版本，一轮运行绑定当时采用的配置，而不是永远指向工作区里最新的文件。复盘打分需要能回到那一轮看到的产物。把追踪推到外部平台可以后做；先保证本仓库的运行记录能按 `thread_id` 找回节点输出。

来源：[Dify Workflow Studio](https://dify.ai/zh/workflows)。

## 5. 不适合照搬的部分

| 做法 | 原因 |
|------|------|
| 在网页上自由拖拽工厂主流程 | 角色、关卡和产物契约写在仓库里。项目只能裁剪节点、绑定场景，不能另画一条主路径 |
| 每个节点各自选模型作为默认做法 | 需求要求优先使用后端的默认模型或模型路由，并复用该后端已有的 MCP、规则和 skill |
| 把 n8n 的数百个 SaaS 节点当作工厂能力 | 工厂的外部动作是角色在目标仓库里写文档和代码，不是替人连接表格和邮件 |
| 把 Dify 的聊天应用当作主界面 | 工厂的主对象是一轮带验收证据的软件交付，不是多轮问答 |
| 用完成百分比表示进度 | 开放式任务估计不可靠。工厂只按已知节点清单标状态 |
| 终端用户各自的 OAuth 凭证体系 | 当前使用者是工厂里的决策者，不是把同一条流程租给许多外部账号 |
| 知识库取代场景配置 | 场景要约束流程、模板和工具，而不只是给模型一段可检索文本 |

## 6. 建议吸收的顺序

按对当前控制台的贴近程度排列。前三项不改 LangGraph 的主路径，只补运行记录和关卡语义。

1. 运行列表与配置版本分开。列表能按运行中、等待人工、已完成、已驳回、已停止筛选。点进一轮，仍用现有节点轨道。
2. 关卡保持「等待」状态并拥有本轮专属的恢复动作。飞书卡片上的按钮对应图上的边。超时未批复要有去向。
3. 失败或退回只重做未完成的节点。已完成节点的产物保留，并在界面上写明这一点。
4. 节点检视分开显示产物、工具调用次数和是否触达重试上限。原始模型输出仍放在折叠处。
5. 场景材料可以单独做一次检查，确认角色会拿到的模板和领域资料，再接入运行。
6. 一轮运行记录它采用的场景和项目配置版本，便于复盘时对照当时的文件。

## 7. 结论

n8n 值得学的是执行语义：暂停要落库、恢复地址属于这一次运行、失败重试不重复已完成的节点、凭证与流程分开。Dify 值得学的是节点契约：人工按钮就是分支、上游产物用变量传递、Agent 的迭代和工具日志单独成档、同一条流程可以测试和发布。

二者的画布都不适合当作 AutoStudio 的主编辑器。工厂的流程仍然由仓库里的图、角色和场景定义。控制台负责把这些定义跑成可查询、可批复、可复盘的一轮。
